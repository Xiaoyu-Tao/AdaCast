Record required generative prediction reasoning decisions in `.forecast/STATE.md`.

Decision paths are mode-isolated:
- When Auto Mode is disabled, use the `ask_*` subcommands. They show the existing built-in user question UI.
- When Auto Mode is enabled, use the `auto_*` subcommands. Start and escalation remain LLM decisions. Test application is policy-driven: every eligible test model defaults to apply without a user question.
- `ask_*` is rejected in Auto Mode, and `auto_*` is rejected outside Auto Mode.

Subcommands:
- `read`: Read the current adjustment decision state and policy.
- `ask_start`: During the forecast phase, after the raw validation search has stabilized and before freezing adjustment source models, ask whether to skip generative prediction reasoning, use lightweight prediction reasoning, or use deep prediction reasoning. Lightweight prediction reasoning uses a compact candidate and rule budget for clear, stable bias patterns. Deep prediction reasoning performs broader evidence synthesis with more candidate iterations. Both remain deterministic and validation-gated. The decision is written to `.forecast/adjustments/policy.json`.
- `auto_start`: Auto Mode only. Pass `auto_start_choice` as `disabled`, `enabled_a`, or `enabled_b`, plus `reason`. The Forecaster LLM should use the frozen task context, quantitative analysis, experiment history, current/per-family best metrics, residual opportunity, evidence quality, and expected adjustment complexity. This records the LLM decision without opening a question window.
- `ask_escalation`: If lightweight prediction reasoning does not produce a validation-accepted skill, ask whether to switch to deep prediction reasoning or end generative prediction reasoning. Switching preserves frozen evidence and adds the deep-reasoning candidate budget on top of the completed lightweight attempts. Ending records a no-effective-skill adjustment decision.
- `auto_escalation`: Auto Mode only. Pass `auto_escalation_choice` as `upgrade_b` or `stop`, plus `reason`. Switch only when validation-front diagnostics still contain credible, untested, blind-safe structure that warrants deeper analysis; otherwise stop and record no effective skill.
- `prepare_test_applications`: After every successful model in the current Critic test collection has raw test artifacts, pass all run ids in `test_run_ids`. The tool finds every model spec with an exact accepted validation counterpart for the locked skill. Non-matching models remain raw-only.
- `ask_test_application`: Manual mode only. Call after `prepare_test_applications`. Omit `raw_test_run_id` to show one user window for every pending eligible test model, or pass one eligible run id for a single decision. Each decision is independently bound to that test run and its matching validation run.
- `auto_test_application`: Auto Mode only. Call after `prepare_test_applications`. Omit `raw_test_run_id` to record apply for every pending eligible test model. Auto Mode defaults to apply whenever the locked skill has an exact accepted validation counterpart, even when that model is not the raw test-best. `auto_test_application_choice: "skip"` is rejected.

Use this tool instead of a free-form chat decision whenever generative prediction reasoning affects whether adjusted test artifacts are produced.
