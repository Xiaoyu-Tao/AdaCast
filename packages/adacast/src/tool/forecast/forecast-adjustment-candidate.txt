Inspect user expert priors and create, read, or list structured deterministic adjustment candidates. `inspect_user_prior` freezes the exact task prior plus explicitly referenced UTF-8 text/code files under `.forecast/adjustments/user-prior/`; it only reads bytes and never imports or executes a referenced Python file. Candidates contain executable rule specs plus a human-readable SKILL.md body. The tool validates rule shape and the global point-delta bound, and writes candidates under `.forecast/adjustments/candidates/`; it does not impose an executable-rule count limit and does not accept or apply candidates.

Every rule evidence reference must be a canonical `.forecast/adjustments/diagnostics/fit/<fit_run_id>/diagnostics.json` artifact from a completed validation-front fit replay. Held-out validation artifacts, test artifacts, pre-forecast analysis, and raw experiment metrics are not valid rule-design evidence. Ordinary `llm_exploratory` conditions, values, time buckets, and numeric ranges must be observed in those diagnostics.

An explicit `user_prior_mirror` is intentionally separate. It requires an immutable inspection artifact, exact source-excerpt mappings for every rule, `llm_provenance.user_prior_mirror=true`, and provenance for every executable condition/action/bound field. User trigger semantics, direction, time scope, action type, and explicit bounds cannot be rewritten. Trigger values absent from validation-front may remain as dormant blind-safe conditions when the required forecast-time columns are available. Explicit Prompt/reference values are preserved; validation-front matching may fit remaining numeric values; anything still unresolved must be declared and completed by bounded `llm_inferred` analysis before validation-back. `llm_inferred` accepts only numbers or numeric arrays. All user rules share one independently budgeted mirror candidate per frozen source set, so held-out validation cannot be used to retune its numbers and ordinary exploratory iterations remain unchanged. This exception does not relax ordinary exploratory candidates.

Rule conditions are blind-safe selectors over prediction-row metadata and forecast-time covariates only: `always`, `horizon_index_in`, `timestamp_hour_in`, `timestamp_month_in`, `timestamp_time_between`, `raw_predicted_original_between`, `exogenous_numeric_between`, `exogenous_text_in`, `exogenous_text_contains`, `exogenous_bool_is`, and `all`/`any` combinations of those selectors. Exogenous conditions must target non-target CSV columns supplied for the forecast horizon. `day_offset` may be used on exogenous conditions for day-level shifted covariates such as "next day is a holiday/work-resumption event"; only offsets present in diagnostics are valid. Prefer narrow validation-front evidence-backed conditions over broad global corrections.

Rule actions are deterministic: `add`, `multiply`, `clip`, or `add_profile` indexed by `horizon_index`. Use rule `bounds.max_delta_original` for fixed absolute caps such as "increase by at most 3000 original target units" and `bounds.min_delta_original: 0` for up-only corrections. Use `timestamp_time_between` or horizon selectors to express fixed unchanged periods such as keeping 00:00-07:00 untouched.
