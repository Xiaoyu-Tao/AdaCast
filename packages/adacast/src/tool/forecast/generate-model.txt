Run a time-series forecasting experiment. Takes an experiment spec and spawns the Python ML runner. When omitted, `phase` and `eval_split` default to `"forecast"` and `"val"`; the only other supported pair is `phase: "post-forecast"` with `eval_split: "test"`. Contradictory pairs are rejected before a subprocess starts. New validation runs receive an input-contract version in the canonical spec so real frequency-aligned time features and explicit prediction-layout coordinates cannot be confused with legacy cached runs. The frozen ratio or timestamp split contract and task-level `window_stride` are copied from `task.json` and cannot be overridden by an experiment spec. `window_stride` is the unified sliding-window step for training and every evaluation stage, and remains separate from model-internal patch stride hyperparameters. Models and scalers train on the full resulting training split; normal validation evaluates only the held-out back 50% of the resulting validation split, while the front 50% is reserved for optional generative prediction reasoning evidence. Before starting a validation subprocess, the tool enforces the unique-run experiment budget and consecutive-crash threshold directly from history. A deterministic `run_id` whose cache is valid returns as cached; if its prior artifacts are invalid or incomplete, the same run may execute again without consuming another unique-run budget slot. Every execution is appended with a one-based `attempt_index`, and retry crashes still count toward the consecutive-crash threshold. Locally trained models save their final checkpoint, built-in statsmodels models save fitted results, and foundation models retain an immutable repository commit reference. For `phase: "post-forecast"` plus `eval_split: "test"`, `reuse_model_from_run_id` is mandatory and must identify the matching forecast-phase validation run; the final fitted model is loaded for inference and retraining is forbidden. Checkpoint and statistical-result files are SHA-256 verified, while foundation models are reloaded from the exact stored commit. A cached or fresh reused test success also requires matching `model/reuse.json` provenance with `training_performed: false` and the same source artifact hash. Every successful `eval.json` binds its metrics to the exact model artifact plus SHA-256 hashes of `predictions.csv`, `actual.npy`, `pred.npy`, and `train_scale.json`; old or changed combinations are never accepted as cache hits. Writers for the same deterministic `run_id` are serialized by a cross-process lock. Invalid or partial artifacts are cleared before a fresh execution so stale predictions cannot be combined with a new model or reuse provenance. Raw runner logs are saved to `.forecast/runs/<run_id>/train.log`. Do not call this before defining a task with `forecast_task`.

Model selection guidance: Before calling this tool, assess the look-back window's time-series conditions (trend direction, seasonality strength, stationarity via ADF test, volatility via coefficient of variation). Choose the model spec to match those conditions. Built-in statistical names are ARIMA, AutoARIMA, ETS, ExponentialSmoothing, SimpleExponentialSmoothing, Holt, HoltWinters, and Theta. ARIMA accepts `order`; AutoARIMA accepts an optional bounded `candidate_orders` list; seasonal ETS/HoltWinters requires `seasonal_periods`. Stationary or clearly seasonal series favor these statistical models, non-stationary or long-horizon series favor deep learning models (DLinear/PatchTST/TimesNet), and low-data or transfer scenarios favor foundation models (Chronos, Chronos2, TimesFM, Moirai, Sundial, TiRex, TimeMoE). Include a `window_features` field in the spec object to document which conditions influenced model selection for this experiment (e.g., `{ "trend": "upward", "seasonality": "strong", "stationary": false, "volatility": "low" }`). This field is stored with the run record and used by the Critic agent to build the per-condition comparison table.

Foundation model guidance: Foundation models Chronos, Chronos2, TimesFM, Moirai, Sundial, TiRex, and TimeMoE use zero-shot load/predict/evaluate. The validation run resolves the repository to an immutable commit and writes `model/foundation.json`; adjustment-fit and test replays must use that same commit. Do not include train_epochs, learning_rate, optimizer settings, or training-loop hyperparameters in foundation specs. The runner relies on HF_ENDPOINT, HF_HUB_CACHE, HF_XET_CACHE, HF_ASSETS_CACHE, TRANSFORMERS_CACHE, and .forecast/model-cache for mirror/cache behavior. Possible structured runtime diagnostics include cache_config, cache_hit, cache_miss, cache_warning, and dependency_missing; default output remains concise.
